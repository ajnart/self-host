# Omarchy support: evidence and decision

Historical research started 2026-11-16 from repository revision `c8371baa64958daf95972ff32cb4dbe7c2b395d4`. The experiments below refer to the builds tested at the time. See the [current Omarchy handoff](omarchy-handoff.md) and [portable native evidence](omarchy-evidence/README.md) for the later packaged integration.

Detailed historical recordings remain in the original private task report.

## Recommendation

The Omarchy 3.8.5 POC now demonstrates useful App behavior, native Dashboard/App launch, restart persistence and **two real Backup/Restore roundtrips**. Each recovery run saved a spool at 875 g, consumed it down to 775 g, then restored 875 g and its comment. The final native Omarchy browser verified the restored result. PostgreSQL ownership/mode and private archive permissions survived. Recovery evidence, native App evidence.

The released **v1.4.0 Arch package also installed successfully in a separate official Omarchy 4.5.0-3 guest**. A user without docker-group membership ran Doctor and installed Spoolman through ordinary authorized sudo; Project ownership stayed with that user and private credentials stayed mode 0600. Spoolman's vendor create/read/delete API workflow passed. This verifies a bounded package/CLI/sudo/App path on newer Omarchy, with further native-desktop and reboot results recorded separately below. In the persistent 4.5 guest, socket-only boot left Spoolman unavailable; explicit guest-only `docker.service` enablement made the next reboot serve the original vendor before any Docker client or Doctor probe ran. A separate native Foot sudo/cancellation flow passed, and a focused elevated-browser fix made the ordinary-user browser display that saved vendor; the released binary had reported opened without creating a window. Clean-VM evidence.

The first 3.8.5 Backup attempt exposed a real rootful PostgreSQL permission bug. A focused fix in the existing archive/helper boundary resolved it. Native Dashboard use later exposed a separate cached-Doctor defect after Restart; its focused refresh fix passed a same-session red/green replay. The separate elevated-browser defect was then reproduced and fixed on 4.5. Preserve all original failures as evidence, not current outcomes. The fixed development binary and released v1.4.0 are different artifacts. The next decision is a narrow optional package/manual/agent/desktop integration, with explicit ownership and version boundaries.

An optional Omarchy entry point into self-host's existing App lifecycle remains a good next product step. Start with one local Docker web App and the Dashboard/agent handoff. self-host already has Arch release packaging; it adds App Setup, Links, Addresses and Backup/Restore to existing Docker tooling. The strongest direct user request names Docker web App launch, readiness, persistence, updates and port conflicts; it is one report, not broad demand. [Existing Arch packaging](https://github.com/ajnart/self-host/blob/c8371baa64958daf95972ff32cb4dbe7c2b395d4/.goreleaser.yaml#L79-L103), [direct request #3797](https://github.com/omacom/omarchy/discussions/3797).

Offer four upstream options: package/manual, a terminal menu entry, agent cross-routing and a later optional Server service entry. Start with package/manual plus routing and pilot the verified desktop launcher; generation-specific menu edits remain a proposal. Omarchy Server is an upstream proposal with an open starter PR, not a released server target. Architecture review and implementation selection follow this evidence; no new module or interface is selected here. [Server plan](https://github.com/omacom/omarchy/blob/quattro/plans/server.md), [starter PR #10952](https://github.com/omacom/omarchy/pull/10952).

## Platform constraints that affect the product

Omarchy is a desktop environment based on Arch, Hyprland and, in the current generation, Quickshell. Sleep, user login, encrypted boot and changing laptop networks affect App availability. Its server effort is separate. A local desktop App and an always-on home server are different use cases; Access must remain an explicit choice. [Released welcome](https://github.com/omacom/omarchy/blob/v4.5.0/manual/01-welcome-to-omarchy.md), [sleep behavior](https://github.com/omacom/omarchy/blob/v4.5.0/manual/36-system-sleep.md), [Server plan](https://github.com/omacom/omarchy/blob/quattro/plans/server.md).

### The newer authorization gap

Released 4.5's lazydocker wrapper uses polkit, but copying it directly for self-host would violate current ownership behavior. `pkexec` supplies `PKEXEC_UID`; self-host recognizes only a root process with sudo's `SUDO_USER`/`SUDO_UID`/`SUDO_GID`. Bare polkit execution would select root as Project owner and, without an explicit Home folder, root's default Project. Passing only `SELF_HOST_HOME` would still leave root ownership. This source-level gap remains; the clean VM demonstrated the supported sudo owner contract instead. The separately verified browser fix runs an elevated opener as that existing owner; it adds no `PKEXEC_UID` recognition or native polkit authorization route. [Tagged wrapper](https://github.com/omacom/omarchy/blob/v4.5.0/bin/omarchy-launch-docker-tui), [official polkit contract](https://www.freedesktop.org/software/polkit/docs/latest/pkexec.1.html), [owner.go:11](../../internal/system/owner.go#L11), [Project:41](../../internal/project/project.go#L41).

The exercised native launcher therefore uses the existing **visible-terminal sudo** route when the inspected standard local socket is inaccessible. It passes explicit public Home folder/Compose Project values, pins the same local Docker endpoint after sudo, and lets sudo supply the real owner fields. It does not synthesize identity, use `sudo -E`, change groups/socket permissions or add a privileged daemon. Seven earlier unprivileged fixture cases passed for direct access, context precedence, remote/custom/missing sockets and the denied standard-socket route. No real sudo/polkit authentication occurred in that fixture; its denied branch was explicitly simulated. Executable proposal and evidence.

The elevated Dashboard's normal-user browser handling remains a separate acceptance case; the 3.8.5 native browser proof ran under the ordinary user. The permission POC includes a small manual/menu proposal but installs neither. Native polkit support, if wanted, should be reviewed in the existing owner boundary rather than inferred from lazydocker's wrapper.

### Actual agent-routing runs and one revision

The static patch is now accompanied by **three actual local Codex CLI runs** using narrowly scoped project-local candidate skills and a read-only adapter. Inputs were an actual sanitized Status capture from the physical 3.8.5 scratch Project and the actual installed local self-host guide; no live 4.5 Project was operated by the model. All three tried `self-host skill core`, received the captured real unsupported-topic error and followed the existing plain `self-host skill` fallback. The inventory trial reported Spoolman's Address with snapshot/local-only limits. The two restart trials proposed a plan without executing it. Each completed with exit **0**, five recorded read commands and identical before/after scratch hashes. Exact runs, prompts and limits.

The first restart plan omitted downtime and useful App acceptance. Only the experimental Omarchy review paragraph was revised; the repeated prompt, captured Status, self-host router, guide, policy and adapter stayed byte-identical. The third run named database/storage location as unknown and proposed inspecting it before approval, recording a known spool's values, a brief interruption, preserved data/local-only Access, then fresh Status and checking those spool values after an approved restart. Restart and verification remained unperformed. This is one observed improvement, not a reliability estimate or proof that the pointer alone caused it. Instruction diff and controls, actual before/after screenshot, interactive transcript viewer.

Both skills were read, and the explicit read-only policy plus adapter supplied extra safeguards. No production skill/config was installed, no personal credential/Profile/session store was inspected by a recorded command, and no other Codex chat was messaged. The screenshots show a labeled local transcript viewer with real recorded output; they are not native Omarchy screenshots. This preserves [ADR 0007's single self-host skill](../adr/0007-one-repo-go-cli-only.md) and [ADR 0005's approval boundary](../adr/0005-agents-load-the-skill-on-their-own.md).
