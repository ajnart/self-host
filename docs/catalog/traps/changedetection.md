# Changedetection.io traps

## Deployment and runtime hold

- The official stable image is `ghcr.io/dgtlmoon/changedetection.io:latest`, with container TCP port 5000. The App defaults to host port 5050 to avoid the upstream-documented macOS AirPlay conflict. `${BIND_IP}` and the allocated host port retain the selected Access; other Apps use service `changedetection` at port 5000.
- Persist the entire App-local `./data` at `/datastore`. It contains settings, API identity, watches, snapshots and private notification/session-related state. Keep it private and preserve it during restart, update and non-purge removal; do not read browser profiles or replace an existing datastore.
- Basic HTTP watches and read-only API statistics do not require a database, external account, browser sidecar, plugin or Docker socket. JavaScript/browser-step watches need a separately selected supported browser backend. This App does not install one, grant capabilities, enable local-address scraping or change browser settings.
- New Compose disables the upstream version-check/telemetry request using supported `DISABLE_VERSION_CHECK=true`. This does not suppress watch activity or prove that startup is otherwise contained.
- **Runtime is held.** The official default startup creates external demo watches for Hacker News and the Changedetection.io changelog on a fresh datastore. No supported no-demo CLI/environment switch was established for the researched image. App preflight returns an actionable Manual error before managed install/start/restart/update/restore, regardless of files or supplied credentials. Do not bypass it with an empty-directory assertion, a fresh flag, guessed JSON, internal datastore mutation, a custom initializer or deletion of matching watches. Existing files are not evidence of creation authority.
- Standalone Compose remains an official deployment definition, not a safe fresh-start acceptance claim. Do not run it on a fresh datastore until an upstream-supported no-demo configuration and separately approved execution exist. A manual review or supplied API key does not automatically lift the code's hold.

## Safe existing-instance Setup

- This partial App slice verifies only an already-running, explicitly configured App. It does not bootstrap an administrator, change passwords, acquire a token from disk, create a watch, invoke rechecks, send notifications or perform browser steps.
- Changedetection.io has one password-only web identity. Verification uses the shared Admin password through the normal CSRF-protected login, a new in-memory helper session and authenticated Settings readback. Anonymous Settings must redirect to the same-origin login. Existing unknown passwords and absent/disabled protection remain Manual; do not change the shared Admin login to conceal a mismatch.
- The existing instance API key is a private recovery input named `api_key`, saved as `CHANGEDETECTION_API_KEY` through the Project secret boundary. It is not randomly generated by self-host. The supported private file input is `--set-file changedetection.api_key=PATH`; the startup hold still prevents installation, so this is not a command to bypass the hold or replace existing Compose.
- Recover the known key privately from Settings > API or an authorized credential backup, restore it through the Project secret boundary, then retry `self-host setup changedetection`. A lost/rejected value remains Manual. Setup never calls Reset API key, automatically recaptures a replacement, reads private datastore files, or invents an issuance journal.
- The API accepts `x-api-key`. Its single instance key is write-capable; there is no inspected scoped/read-only alternative. Setup consumes only the saved key and never prints credentials, settings HTML, watch titles/Addresses or raw response bodies. Missing prerequisites stop before peer requests.
- Positive verification requires authenticated `/api/v1/systeminfo` with a supported version (0.60.10 or later), explicit nonnegative uptime and integral watch count, plus `/api/v1/watch` as an explicit object with finite nonnegative `last_changed` and boolean `viewed` on each entry. Missing/null/invalid data is not zero. Separate reads can change during ordinary operation, so their totals are not compared as a single snapshot.
- Missing and invalid keys must both receive HTTP 403. Setup does not enable/disable API enforcement to turn a hold into success. Exact read-only GETs omit `recheck`, `recheck_all`, `paused`, `muted` and all other action parameters; upstream supports mutations through some GET endpoints.

## Remaining acceptance

Automatic no-demo deployment/bootstrap is not implemented. This App is not yet centrally registered, and no native Homarr leaf or Stats binding is included in this slice. Connector work waits for reviewed shared contracts; do not paste temporary issuance/count helpers.

The researched Homarr kind is `changedetection`, with only `apiKey`. Shared Stats exposes `diffsDetected` (unviewed watches whose `last_changed > 0`) and `totalObserved` (watch count), both in `count` units. A valid authenticated empty instance can legitimately report both as zero, but native acceptance still requires a genuinely advancing shared refresh and positive connection identity. No external watch or scrape should be created to populate a widget.

Focused fake/source checks are not live deployment, rendered-widget, lifecycle, Backup/Restore or install-order acceptance. Those require separately approved, centrally scheduled isolated attempts after the startup hold is safely resolved. Preserve real watches, sessions and notification destinations throughout.
