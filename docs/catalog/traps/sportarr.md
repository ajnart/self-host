# Sportarr traps

## Deployment and storage

- The official image is `sportarr/sportarr:latest`, serving its web interface and API on TCP 1867. SQLite is built in. PostgreSQL is optional and its documented selection is fresh-install-only; this App neither adds a database service nor migrates a database provider.
- `/config` contains Sportarr's configuration, SQLite data and logs. The supported fully non-root `user: UID:GID` mode avoids the image entrypoint's recursive ownership changes. The selected user must already be able to write the App's configuration directory. Non-root mode ignores PUID/PGID environment variables; UMASK and TZ remain supplied. No devices, privileged mode, root startup script or Docker socket are required.
- Shared media Projects receive one `${DATA_ROOT}:/data` mount. Legacy layouts retain `${MEDIA_ROOT}:/media` and `${DOWNLOADS_ROOT}:/downloads`; changing existing roots is an explicit migration, not Setup. No root folder, library, event, downloader, profile, naming setting or DVR schedule is created or changed. A common mount is not proof of an actual hardlink import, and separate media identities are not enabled by this App.

## Setup and recovery

- This initial App slice verifies an **existing** Forms administrator using the shared Admin login from `self-host credentials`. Fresh/unconfigured accounts, a different administrator, Basic/external authentication or authentication bypass for local addresses remain retryable Manual steps. Setup does not infer account ownership from an empty instance or change security settings. Automatic first-account configuration is not implemented.
- Sportarr is not Sonarr. Verify native `GET /api/system/status`, including `appName: Sportarr`, a numeric 4.x version and `authentication: apikey`. Its intentionally compatible `/api/v3/system/status` identifies as Sonarr and cannot establish Sportarr identity. `/ping` and HTTP 200 alone are insufficient. Unknown native major versions require review, not a forced auth rewrite.
- Login is JSON `POST /api/login`, followed by a `SportarrAuth` HttpOnly session cookie and an authenticated `/api/auth/check` identity. Setup reads native `/api/settings`, whose `securitySettings` is a JSON-encoded string, and requires Forms authentication for every address and the expected username. It closes each temporary verification session, never persists its cookie and does not borrow an HTTP client's ambient cookies.
- If no saved key exists, Setup can read the current master API key **only through the positively verified existing login**, verify native identity and anonymous/invalid-key rejection, then save it as `SPORTARR_API_KEY` through the private Project secret boundary. It does not use unauthenticated `/initialize.json`, scrape configuration/database files, issue a key or call the global regeneration endpoint. The inspected API has no dedicated read-only-key alternative. Do not assume the startup `Sportarr__ApiKey` variable supplies the key: the real authentication handler reads the App's configured master key.
- Valid saved credentials are reused. A rejected saved key is never silently replaced, even when the administrator can sign in. Restore matching credentials using the private Project recovery boundary, then retry `self-host setup sportarr`. The optional `api_key` input uses an owner-only `install --set-file sportarr.api_key=PATH` import; **the current `setup` command does not accept `--set-file`**. Install can replace the Compose definition: preserve/review existing image, mounts, ports and authentication and separately approve that replacement before using install for credential recovery. Do not casually reinstall or regenerate the master key.
- Setup performs no PUT to `/api/settings`. A security-only payload would reset unrelated flat settings to defaults; replaying the entire response can also rewrite library/naming configuration. That API is not the Servarr `/config/host` contract. Account/bootstrap automation needs its own safe reviewed continuation.

## Remaining acceptance and runtime hold

- No Catalog registration, Homarr descriptor or native widget is included in this App-only slice. Homarr's exact kind is `sportarr`, using `apiKey`; its supported native surfaces are `calendar` and `mediaMissing`. A Sonarr-like adapter method or an upstream provider's existence does **not** admit Sportarr to Stats: no Sportarr Stats widget/metrics are configured.
- Later connector work must consume the reviewed shared calendar/media-organizer readers owned by #147, preserve both install orders and managed/unmanaged bindings, and separately establish useful native, rendered and lifecycle acceptance. It must not seed events or download media for an acceptance value; authenticated empty data may be legitimate but missing/null/error responses are not zeros.
- **Runtime remains held.** The upstream image starts background services for metadata/hub synchronization, indexers/downloads, DVR, maintenance and import lists. Its default `SendAnonymousUsageData` is true. This slice does not rewrite existing schedules or claim a no-network startup configuration. Before any isolated runtime attempt, the coordinator must contain relevant startup/outbound behavior through supported configuration or retain the hold. No runtime, native, rendered, import, identity-mapping or lifecycle acceptance is established by source/HTTP-fake tests.
