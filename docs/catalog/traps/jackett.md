# Jackett traps

## Deployment

- Uses the existing DCM product ID `jackett` and supported vendor image `ghcr.io/hotio/jackett:latest`, not an image published by the Jackett project itself. Hotio documents TCP 9117, `/config`, PUID, PGID, TZ and UMASK. The Project binds the selected host port and Access to container port 9117 and retains App-local configuration on ordinary removal.
- Hotio's launcher uses `--NoRestart --ListenPublic --NoUpdates --DataFolder=/config`. Container listening is separate from the Host's selected Access. Do not enable public Access, a VPN, extra capabilities or host networking just to pass Setup. LinuxServer-specific `AUTO_UPDATE` and `RUN_OPTS` are not Hotio settings.
- The App needs no database, media mount, downloads folder or other backing service. `/config` contains the instance key, `Indexers` configuration, tracker credentials and data-protection keys; keep it private and back it up. FlareSolverr, OMDb, accounts and tracker selection remain optional person-owned choices.

## Setup and recovery

- Jackett's administrator login uses only a password. Setup tries the saved private `admin_password` input, otherwise the shared Admin password. It verifies the returned session by reading authenticated configuration, requiring a nonempty password marker, a supported version and an instance key, then proving anonymous configuration access is denied. A redirect, cookie or `/health` response alone is not authentication.
- **Automatic first-password bootstrap is not implemented in this App-only slice.** A new instance without an administrator password remains Manual, even though upstream permits an empty-password session. That is not proof of first-run ownership. Open Jackett and set the first administrator password yourself before sharing access, then run `self-host setup jackett`. Existing passwords are never overwritten or disabled.
- A positively authenticated existing administrator may read its already-issued instance key through Jackett's configuration API. Setup validates that key against capability and configured-indexer metadata before saving it through the existing Project secret helper. No key is created or rotated. A valid saved key is reused; a saved key differing from the authenticated instance key remains Manual instead of being replaced.
- For a lost/rejected password or mismatched saved key, use `self-host credentials` privately and recover the existing credential deliberately. Optional `admin_password` and `api_key` inputs are private, recovery-only inputs accepted through the existing `--set-file` install boundary. Reinstall changes Compose: review and separately approve preservation of existing ports, mounts, image selections and edits before using that boundary. Never pass a password/key directly in arguments or chat, scrape private configuration files/databases, or reset tracker credentials.
- Authenticated `app_version` is checked against the inspected 0.24.2994 contract, allowing later 0.x versions rather than a release allowlist. Missing/malformed version, password state or key data cannot complete Setup. Unknown custom base paths/authentication stay explicit recovery boundaries; Setup does not rewrite them.
- The complete configuration response can contain unrelated proxy/account secrets. Only required fields are decoded, the response is never logged, and failures use fixed diagnostics instead of raw response/error snippets. Requests retain normal trusted TLS and same-origin credential handling.

## Read-only verification and preservation

- Only `t=caps` and `t=indexers&configured=true` are requested from `/api/v2.0/indexers/all/results/torznab/api`. These return local metadata before Jackett's search path. The App never adds or edits an indexer, tests trackers, searches releases, downloads, updates server settings or shuts down Jackett.
- Invalid Torznab API keys can return **HTTP 200 with XML `<error code="100" .../>`**. Setup requires the expected XML root, complete well-formed content, Jackett's capability server title and explicit search availability, and valid configured-indexer metadata. Reading search availability does not execute a search. Empty `<indexers/>` is legitimate after authentication; missing IDs/titles/configured state, duplicate IDs, XML errors, text-only catalogs and trailing roots are not fabricated zero counts.
- The instance key is unscoped: upstream offers no dedicated read-only key alternative. Read-only verification does not make the credential itself read-only. Keep it private and do not expose it to unrelated Apps.
- Reruns preserve the existing password, key, configured trackers, paths, cache, proxy/FlareSolverr settings and accounts. No Links to download clients or media Apps are added by this slice.
- Startup/outbound behavior has not been runtime-audited here. No Docker, browser, tracker/account operation or real Project was used. Source/fake-backed Setup checks do not prove native Homarr, rendering, both installation orders, removal/reconnect or cross-kind survivor acceptance.

## Deferred Homarr work

Homarr's exact kind is `jackett`, credential alternative `apiKey`. Its read-only Stats metric is `configured`, unit `count`; an authenticated zero is valid. The `indexerManager` list reports unknown health, not healthy trackers. Its optional **test all** action performs tracker searches and must never be used for verification. The connector, reviewed shared count/envelope helpers, Catalog/target registration, generated metadata/counts and isolated acceptance remain coordinator-owned follow-up work, not completed coverage.
