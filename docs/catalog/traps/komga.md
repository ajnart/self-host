# Komga traps

## Deployment and persistence

- The official image is `gotson/komga:1.x`, with one container and web/API port `25600`. The maintainer explicitly approved Komga's official `1.x` major track as an App-local exception; this does not change the global image policy. The major tag floats; record the resolved image and running version separately when validating an installation. It needs no separate database or queue service. [Official Docker guide](https://komga.org/docs/installation/docker/)
- The App declares `config` mode `0700` for the actual selected decimal `${PUID}:${PGID}` runtime identity through the reviewed `DirectoryDeclarer` action. Install and accepted generated-definition refresh prepare/admit it before startup. The long configuration bind sets `create_host_path: false`, so Docker cannot silently recreate a missing source as root-owned storage on later starts. No default-to-root identity, sentinel file or account-absence authority is inferred from directory creation.
- Preparation admits only the reviewed local Linux filesystem/ACL, ownership-mapping, trusted-parent and Project-lock boundary. Existing compatible storage and children are unchanged; symlinks, unknown/present ACLs, mismatched ownership or broader permissions remain Manual without recursive repair or migration. Preserve the existing data and review the specific hint; do not reset ACLs or re-own the tree to silence it. Native Linux positive directory preparation and actual container writability remain unverified on this macOS development host; source/fake tests are not full-App/runtime acceptance.
- The `./config` bind at `/config` keeps the main SQLite database, tasks database and application configuration together. Configuration must stay on a local filesystem, not CIFS/NFS; do not disable Komga's filesystem safety check. Preserve this folder across restart, update and non-purge removal. [Configuration](https://komga.org/docs/installation/configuration/)
- The image supports numeric `user:`; the App uses the shared Host UID/GID and time zone, not LinuxServer-only environment variables. Existing ownership is not migrated or recursively changed.
- Books are mounted from the Host media folder's `books` subfolder to `/data` read-only. They are external media, not configuration Backup contents. Import, file deletion and other writable-library features are not enabled by this definition. Changing storage paths or permissions needs an explicit preservation/migration decision.

## Administrator Setup and recovery

- The Admin email is the shared Admin username followed by `@selfhost.local`; the password is the Project's shared Admin password. `self-host credentials` shows the App's email alias without Setup printing a password.
- Setup first verifies HTTP Basic `GET /api/v2/users/me`: a nonempty user ID, exact intended email and explicit `ADMIN` role are required. It keeps the accepted ID privately as `KOMGA_ADMIN_USER_ID`. Subsequent checks reject a different ID; matching email alone cannot replace the recorded administrator.
- The official unauthenticated `GET /api/v1/claim` reports `isClaimed` from whether any users exist. Only an explicit boolean `false`, checked again immediately before mutation, permits the existing first-admin helper to call `POST /api/v1/claim` with `X-Komga-Email` and `X-Komga-Password` headers. Missing, null, malformed or inaccessible claim status is not proof of absence. [Claim controller, Komga 1.29.2](https://github.com/gotson/komga/blob/829f75884b013037a0ed74c6d8966c8857b35d9c/komga/src/main/kotlin/org/gotson/komga/interfaces/api/rest/ClaimController.kt)
- A claimed server, rejected intended login, changed recorded identity or uncertain response stays Manual when it cannot be positively verified. Open the App, review the email/password through `self-host credentials`, restore the confirmed matching Project login privately if needed, then run `self-host setup komga`. Do not reset the database, replace a user's password/account, clear a recorded identity to authorize registration, or change Access/TLS trust to make a check pass. An interrupted successful claim is recovered by verifying the same intended login, not blind registration.
- The first administrator receives Komga's full administrator roles; this is not a least-privilege Homarr credential. Administrator bootstrap does not issue an API key. Setup does not download, stream, import or scan books, create libraries, change reading progress or alter sharing policies. Existing users, paths, libraries and progress remain untouched. [User controller](https://github.com/gotson/komga/blob/829f75884b013037a0ed74c6d8966c8857b35d9c/komga/src/main/kotlin/org/gotson/komga/interfaces/api/rest/UserController.kt)

## Native Homarr and selected credentials

- Setup never creates another user. Explicitly select a confirmed existing limited account using private `homarr_user_id`, `homarr_user_email` and `homarr_user_password` inputs through owner-only files and `install --set-file`. Its authenticated `/api/v2/users/me` identity must match the selected ID/email, have exactly `USER`, all-library metadata access and no age/label restrictions. Account creation or policy changes remain the person's separate decision, not an automated prerequisite workaround. Reinstalling with inputs replaces Compose and needs preservation/review and separate approval; never reinstall blindly.
- An unselected standalone App skips Homarr credential preparation. If Homarr is installed, or any selected/credential/journal value exists, Setup verifies or prepares that selected account's key. A peer-first install without a selection remains explicit Manual when Homarr later asks to link; complete the private selection and run `self-host setup komga`, then `self-host setup homarr`. No scheduling bypass or empty credential alternative is used.
- Komga keys inherit their user's permissions; there are no independent read-only key scopes. The selected account excludes administrator, download, page-streaming and sync roles, but still has ordinary account/metadata rights, including its own progress/key management. It must not be described as a strictly read-only scoped token. [Key authentication](https://github.com/gotson/komga/blob/829f75884b013037a0ed74c6d8966c8857b35d9c/komga/src/main/kotlin/org/gotson/komga/infrastructure/security/apikey/ApiKeyAuthenticationProvider.kt), [roles](https://github.com/gotson/komga/blob/829f75884b013037a0ed74c6d8966c8857b35d9c/komga/src/main/kotlin/org/gotson/komga/domain/model/UserRoles.kt)
- App-owned issuance uses the reviewed shared `CredentialIssuance` operations `Pending`, `Begin`, `Capture`, `Commit`. Before one POST to `/api/v2/users/me/api-keys`, Setup positively verifies the intended administrator and selected limited user, and checks that no existing key has the managed comment. The one-time response secret and selected metadata are captured before status/semantic acceptance. IDs, owner, dates, comment, secret fingerprint, live key-authenticated identity and exact key inventory membership are verified before committing the active pair.
- Valid App-owned keys are reused. Unowned comment collisions, missing/rejected/mismatched saved records, transport uncertainty and partial issuance stay Manual without reissuing, adopting, revoking or clearing anything. Exact captured evidence can only finish the same verified tuple. Private `KOMGA_HOMARR_KEY_PENDING` holds uncertainty; `KOMGA_HOMARR_KEY_OWNERSHIP` and `KOMGA_HOMARR_API_KEY` hold the accepted local pair. Restore only the confirmed matching private records; never clear a journal to authorize replacement. The redacted inventory does not reveal the secret or independently identify which key authenticated. The original issuance capture/fingerprint binds the local credential, not Homarr's saved secret. [Redacted key DTO](https://github.com/gotson/komga/blob/829f75884b013037a0ed74c6d8966c8857b35d9c/komga/src/main/kotlin/org/gotson/komga/interfaces/api/rest/dto/ApiKeyDto.kt)
- The supported Homarr surface is Stats with `libraries`, `series`, `books`, all counts. No library/series selector or book download is needed for legitimate empty-library counts with positively authenticated identity. [Homarr Komga guide](https://homarr.dev/docs/integrations/komga/)
- **Managed native linking is held Manual before common reconciliation in both Check and Apply.** Two valid keys A/B belonging to the selected account produce the same `/api/v2/users/me` identity and redacted account-key inventory. Neither that identity/rights result nor the local issuance fingerprint proves Homarr saved A rather than B. The supported inspected APIs supply no authoritative exact saved-key proof. Preserve B, existing integrations/widgets/layout and local ownership records, including on Address or fingerprint drift; do not rotate, replace, inspect private databases/decryption internals or reinstall to bypass the hold. Keep any person-managed connection unchanged and wait for a supported verification contract before retrying `self-host setup homarr`. Removal remains independent of peer credentials/preflight.
- Account diagnostics decode the actual Homarr proxy envelope: the parsed Komga `UserDto` is **directly in `data`**, not `data.response`. [Pinned request executor](https://github.com/homarr-labs/homarr/blob/df8d03b13452bb50c55a424187e1fa188ab510d2/packages/custom-widgets/src/server/request-executor.ts#L130-L139), [proxy return](https://github.com/homarr-labs/homarr/blob/df8d03b13452bb50c55a424187e1fa188ab510d2/packages/api/src/router/integration/integration-request.ts). Successful account diagnostics still return the defensive exact-key Manual hold before any Stats acquisition. Source-shaped account and Stats positive controls are not production connector completion. Wrong integration/account/roles and invalid counts/units/retry/freshness remain rejected by their respective checks. Registry/site/DCM assembly remains coordinator-owned.
- Runtime, startup/outbound behavior, rendered widgets, both installation orders and ownership-preserving removal/reconnect remain unverified and centrally held. Do not execute them as part of this source-only slice.
