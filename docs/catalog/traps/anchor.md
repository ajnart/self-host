# Anchor traps

This is the offline-first notes product [ZhFahim/anchor](https://github.com/ZhFahim/anchor), not another product named Anchor. This App-only slice implements deployment and verified existing administrator/read access. Automatic first-account creation, Homarr credentials, native wiring, rendered widgets and lifecycle acceptance are not complete.

## Image, storage and Access

- Official image: `ghcr.io/zhfahim/anchor:latest`. Research resolved version `0.17.2`, source `43a1ad09d23b971d34a9c7df4c49e52c2c5a21da`; resolve mutable tags again before runtime acceptance.
- One image includes PostgreSQL 18, the API and the web interface. Publish only port **3000**. API port 3001 and embedded PostgreSQL at `127.0.0.1:5432` stay unpublished. Homarr's advertised default 8080 is not the official image's port.
- The App-local `./data:/data` bind preserves `/data/postgres`, uploads and the image-generated `/data/.jwt_secret`. Back up the whole directory; ordinary removal retains it. Do not inspect the signing-secret file, scrape the database, regenerate credentials to repair auth, or point existing data at a different PostgreSQL major.
- Keep the image's supported startup identity. Its entrypoint initializes and adjusts ownership of its PostgreSQL directory; self-host adds no PUID/PGID, `user:`, recursive host migration, Docker socket or privileged access.
- `APP_URL` uses the direct browser Address for the selected local/Home network Access. Preserve any edited proxy/OIDC/CORS configuration and set the actual browser Address before enabling those optional features. Internal integration Address would be `http://anchor:3000`, not the browser Address.
- Registration is **enabled by upstream default**. This source slice does not execute the image or claim safe unattended first startup on an untrusted network. Initial runtime remains held for an explicitly approved private disposable attempt. Deliberately establish the first administrator only on a genuinely new instance, then review registration through Anchor's admin settings before untrusted access. Do not reopen registration on existing data to satisfy Setup.

## Administrator and Manual first account

- Setup verifies `/api/health` product/version, then signs in using the shared Admin password and the intended email. The default App-local alias is `<ADMIN_USER>@selfhost.local`; an explicitly selected existing email may be supplied privately as `anchor.admin_email`. No existing account is renamed to match the alias.
- `POST /api/auth/login` returns a short-lived JWT plus ordinary session material. Setup verifies the login response and **JWT-authenticated** `GET /api/auth/me`: a nonempty matching ID, exact intended email, explicit administrator flag and active status are required. The helper keeps only the access JWT in invocation memory and discards returned refresh material; no JWT replaces a saved permanent token.
- The first positively verified intended existing account is recorded privately as `ANCHOR_ADMIN_IDENTITY`, JSON `{id,email}`. This is a stable selected-account record, not a claim that self-host created/owns that user. A corrupt/mismatched record is preserved and cannot authorize a replacement. With no record, only positive verification of the explicitly intended administrator permits an initial selection; this is not a provenance ledger and cannot detect a deliberately erased selection. Login failures, pending/OIDC-only accounts and uncertain recovery remain actionable Manual.
- Automatic first-account creation is deliberately absent. Ordinary `/api/auth/register` is not first-user-only, and `/api/auth/registration-mode` does not prove no administrator exists. Setup's Manual path never registers, resets passwords, elevates users, creates a household or edits profile/authentication settings.
- After identity verification, a read-only JWT request to `/api/notes?limit=1` checks typed note metadata. An explicit empty array is valid **only alongside independently verified administrator identity**. Missing/null/error data is not zero or success. Note titles/content never appear in diagnostics; no note is selected, written, created or deleted.
- To restore a known selection, use private `anchor.admin_email` and matching `anchor.admin_identity` recovery inputs through approved `install --set-file` ingestion. Empty inputs preserve saved values. Installing replaces Compose: first preserve/review existing mounts, image/auth/Access settings and separately approve replacement. Never guess an ID or change accounts merely to make a check pass. Then run `self-host setup anchor`.

## Homarr integration

With Homarr installed, Setup issues the verified administrator's single permanent token through the shared credential issuance journal and saves it as `anchor.homarr_api_key` with `anchor.homarr_token_ownership` (account ID, email, SHA-256 fingerprint). The token has no scopes and no `/me`, so identity is proven by the account's own JWT: `GET /api/auth/api-token` must return exactly the saved token, and `/api/notes?limit=1` must accept it. Homarr consumes it as kind `anchor`, credential `apiKey`, Stats metric `notes` (`count`, accessible notes, including shared ones). Zero is a valid count only once that account binding holds.

An existing token self-host did not issue, a replaced or revoked token, a mismatched ownership record or an interrupted issuance stops as Manual: self-host never regenerates over an unrecorded token. The token can write the selected administrator's notes; a dedicated non-administrator account is not created.

`anchorNote` needs deliberate selection of a real existing note and consent to display its private content, so it is not wired. Native/rendered/Stats freshness, both installation orders and owned-only remove/reconnect preservation still require runtime verification.
