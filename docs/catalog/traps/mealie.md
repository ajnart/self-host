# Mealie traps

## Deployment and persistence

- The official image is `ghcr.io/mealie-recipes/mealie:latest`, inspected at v3.30.0/source `9552df62118224a377d9c9b0a62706a62220ab86` on 2026-11-02. Upstream recommends explicit release tags and deliberate updates; the Catalog currently uses floating App tags. Preserve an existing person's image selection and inspect release notes before updating.
- One service publishes host port 9925 to fixed container port 9000, using the selected bind address. Internal connections use `http://mealie:9000`, not the host port or a browser Address. The image supports PUID/PGID/TZ; this App adds no socket, device, elevated capabilities or identity override.
- SQLite needs local storage. The complete `./data:/app/data` bind contains recipes/assets, users, households, SQLite, backups and upstream-generated signing/session secrets. Keep its exact storage identity across restart, update and non-purge removal; never read, regenerate or replace the signing files. Network-attached storage needs a separately approved PostgreSQL plan, not an automatic database migration.
- The image's own root-start entry script recursively adjusts ownership under `/app` before switching user. Review existing data ownership before changing PUID/PGID; self-host adds no separate recursive ownership operation.
- Signup is disabled; a 1000 MB memory limit follows upstream guidance. Basic password/API operation uses the upstream default request-origin behavior. Configure a person-owned BASE_URL explicitly when using mail/OIDC callbacks; it is a browser Address, never `http://mealie:9000`. Do not broaden Access, change authentication or disable TLS verification for a successful check.

## Existing-account verification only

- This remains a **partial implementation** of #165: initial-account bootstrap is Manual and no runtime/native/rendered acceptance is claimed. Setup never creates users/groups/households, changes profiles/passwords, imports/scrapes recipes or edits meal plans. It authenticates an already intended account through `/api/auth/token`, verifies `/api/users/self` and `/api/households/self`, and may issue one named Homarr token only after explicit account/group/household selection and complete collision-free inventory verification.
- Complete the initial account manually. Current upstream does not support configuring the seed email/password through DEFAULT_EMAIL/DEFAULT_PASSWORD. Its startup first-login flag only reports that the factory-email account exists; it does not authorize taking over that account. The factory administrator remains Manual even when its IDs are explicitly supplied. No fresh boolean, empty-directory inference or provenance journal is added.
- Explicitly select the existing administrator, group and household using private inputs `mealie.admin_user_id`, `mealie.group_id` and `mealie.household_id`. Values are UUIDs from the intended account's authenticated user and household information, not guessed names. They select verification identity only; they grant no ownership or mutation authority. The shared Admin login must authenticate that same selected administrator by username or email. A different account/household, incomplete data, rejected credentials, missing selection, demo instance, disabled password authentication or unsupported API version does not pass.
- Provide confirmed selections through the Project's approved private-input boundary (`install --set-file` with owner-only input files). Empty inputs preserve saved values. Reinstall can replace Compose: preserve/review existing authentication, image, mounts, ports and manual edits and obtain separate approval before using it for input recovery. Never quote credentials, replace the shared Admin login automatically or reset users/households/recipes to resolve a hold. After approved recovery, retry `self-host setup mealie`.
- Login sessions stay in memory for one helpers invocation and are not written as long-lived credentials. A rejected login is remembered for that invocation to avoid repeated failed password attempts across Step checks. Every verification still rereads authenticated account and household identity; a cached session alone is not success. API errors and Manual hints never print response bodies, returned IDs or credentials. The separate Homarr token and ownership are private Project credentials.
- Current admission is Mealie 3.30.0 or a later same-major version with complete production/password API identity. An unexpected major/version remains Manual for source review, not permission to replace its image or data.

## Credential and native connector boundaries

- The reviewed helper bundle `887acc1eea667ae2f1f3487851f5b7e7ab249b3e` supplies the four `CredentialIssuance` journal operations and shared Homarr count validation. Mealie owns provider-specific identity, token inventory and semantic validation; no journal/count/envelope clone or automatic dedicated-user creation is added.
- Mealie API tokens inherit **full access to the selected administrator account**, including its write/administrative authority, with no read-only scopes. Household-scoped statistics are not a security restriction on the token itself. The token is named `self-host Homarr statistics`; issuing it does not create or move users. Upstream issues long-lived tokens for five years; rejection/expiry never authorizes automatic renewal or replacement. A separate less-privileged account would require a separately approved account choice, not a silent fallback or automatic account creation.
- Private records are `MEALIE_HOMARR_API_KEY`, `MEALIE_HOMARR_KEY_OWNERSHIP` and `MEALIE_HOMARR_KEY_PENDING`. The immutable intent/ownership identify the selected existing user, group and household, requested integration attribution, explicit full-account authority, returned numeric token ID, creation time and key fingerprint. The JWT's user-ID claim is not the token-record ID. Changing any intended selection holds the old key/intent unchanged instead of adopting it into another household.
- The App writes a shared intent before its one issuance POST, captures a returned one-time token and selected metadata before checking status/IDs/name/time, then freshly verifies token authentication, account/household and exact inventory metadata before shared Commit. Check is read-only. Captured successful evidence may finish only its exact original tuple; intent-only, malformed, non-success, collision, missing/rejected secret or conflicting ownership stays held, never reissued. A partially saved capture may be unavailable after interruption; the intent remains a hold, not exactly-once or power-loss durability proof. Never clear a hold just because an inventory name disappeared.
- Recovery-only private inputs `mealie.homarr_api_key` and `mealie.homarr_key_ownership` restore only a confirmed matching tuple after explicit reconciliation. Preserve any pending evidence privately; do not delete/adopt an API token by name or switch the selected identity to evade it. Review existing Compose replacement and obtain approval before using reinstall for private-input recovery. Retry `self-host setup mealie`, then `self-host setup homarr`.
- The peer-owned key is prepared independently of Homarr's presence, so peer-first installation does not leave an omitted prerequisite for the later consuming Link. Homarr only consumes it. App Check verifies the current key/ownership and identity; the Link never issues/revokes tokens, changes accounts or reads recipes.
- Homarr's exact kind is `mealie`, credential alternative `apiKey`, supported widget shared Stats, reading `/api/households/statistics`. Recipes/users are household counts; categories/tags are group-wide. Homarr advertises `recipes`, `users`, `categories`, `tags`, not `totalTools`. Preflight checks App-owned credentials before mutation. Native verification additionally reads account and household through the **saved integration**, checks returned integration ID/kind and selected scope, then the existing central catalog/snapshot/forced-refresh path supplies exactly one genuinely advancing Stats sample per verification invocation. The peer callback uses shared count helpers, requires count units and finite integral nonnegative values, positive users, successful zero retry metadata and bounded future skew. Recipe/category/tag zeros are valid; null/missing/error/stale/no-op data is not success. Equal empty counts never prove identity.
- Catalog/target registration, generated site/DCM data, global metadata/counts and both installation-order integration acceptance remain coordinator-owned. The unregistered `mealieTarget()` leaf uses existing Homarr ownership/layout/shared-widget mechanisms; no common reconciliation or registry is edited here. Existing DCM Container ID `mealie` merges with an App of that same ID without an alias; its historical image/SECRET_KEY fields are not this App's deployment contract. Removing a Link never revokes the App key or deletes users/recipes/households.
- Focused source/fake verification does not establish actual image startup, native/rendered values, lifecycle preservation, backups/restores, both installation orders or zero outbound behavior of the complete upstream image. No Docker/browser/installer/provider action was executed. Optional scraping, imports, mail/OIDC and upstream scheduled behavior remain outside this slice's runtime evidence.
