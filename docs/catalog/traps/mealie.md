# Mealie traps

## Deployment and persistence

- The official image is `ghcr.io/mealie-recipes/mealie:latest`, inspected at v3.30.0/source `9552df62118224a377d9c9b0a62706a62220ab86` on 2026-11-02. Upstream recommends explicit release tags and deliberate updates; the Catalog currently uses floating App tags. Preserve an existing person's image selection and inspect release notes before updating.
- One service publishes host port 9925 to fixed container port 9000, using the selected bind address. Internal connections use `http://mealie:9000`, not the host port or a browser Address. The image supports PUID/PGID/TZ; this App adds no socket, device, elevated capabilities or identity override.
- SQLite needs local storage. The complete `./data:/app/data` bind contains recipes/assets, users, households, SQLite, backups and upstream-generated signing/session secrets. Keep its exact storage identity across restart, update and non-purge removal; never read, regenerate or replace the signing files. Network-attached storage needs a separately approved PostgreSQL plan, not an automatic database migration.
- The image's own root-start entry script recursively adjusts ownership under `/app` before switching user. Review existing data ownership before changing PUID/PGID; self-host adds no separate recursive ownership operation.
- Signup is disabled; a 1000 MB memory limit follows upstream guidance. Basic password/API operation uses the upstream default request-origin behavior. Configure a person-owned BASE_URL explicitly when using mail/OIDC callbacks; it is a browser Address, never `http://mealie:9000`. Do not broaden Access, change authentication or disable TLS verification for a successful check.

## Existing-account verification only

- This is an **App-only partial implementation** of #165, not automatic initial-account or native Homarr acceptance. Setup never creates users/groups/households, changes profiles/passwords, issues API keys, imports/scrapes recipes or edits meal plans. Its sole POST authenticates an already intended account through `/api/auth/token`; subsequent checks read `/api/users/self` and `/api/households/self`.
- Complete the initial account manually. Current upstream does not support configuring the seed email/password through DEFAULT_EMAIL/DEFAULT_PASSWORD. Its startup first-login flag only reports that the factory-email account exists; it does not authorize taking over that account. The factory administrator remains Manual even when its IDs are explicitly supplied. No fresh boolean, empty-directory inference or provenance journal is added.
- Explicitly select the existing administrator, group and household using private inputs `mealie.admin_user_id`, `mealie.group_id` and `mealie.household_id`. Values are UUIDs from the intended account's authenticated user and household information, not guessed names. They select verification identity only; they grant no ownership or mutation authority. The shared Admin login must authenticate that same selected administrator by username or email. A different account/household, incomplete data, rejected credentials, missing selection, demo instance, disabled password authentication or unsupported API version does not pass.
- Provide confirmed selections through the Project's approved private-input boundary (`install --set-file` with owner-only input files). Empty inputs preserve saved values. Reinstall can replace Compose: preserve/review existing authentication, image, mounts, ports and manual edits and obtain separate approval before using it for input recovery. Never quote credentials, replace the shared Admin login automatically or reset users/households/recipes to resolve a hold. After approved recovery, retry `self-host setup mealie`.
- Login sessions stay in memory for one helpers invocation and are not written as long-lived credentials. A rejected login is remembered for that invocation to avoid repeated failed password attempts across Step checks. Every verification still rereads authenticated account and household identity; a cached session alone is not success. API errors and Manual hints never print response bodies, returned IDs or credentials.
- Current admission is Mealie 3.30.0 or a later same-major version with complete production/password API identity. An unexpected major/version remains Manual for source review, not permission to replace its image or data.

## Deferred connector work

- Reusable non-idempotent issuance waits for reviewed #150; counts/envelope and Homarr connector work wait for reviewed #147 and a new dispatch. This slice has no Homarr descriptor, token metadata journal, temporary helper copy or fallback administrator token.
- Mealie API tokens inherit their user's authority and have no read-only scopes. A later dedicated non-admin identity in the explicitly selected household is preferable to an administrator key, but still has write-capable user access. No account/key is created by this slice.
- Homarr's exact kind is `mealie`, credential alternative `apiKey`, supported widget shared Stats, reading `/api/households/statistics`. Recipes/users are household counts; categories/tags are group-wide. Homarr advertises `recipes`, `users`, `categories`, `tags`, not `totalTools`. Missing data is not zero. Positive identity and advancing fresh Stats are separate requirements, not implemented here.
- Catalog registration, generated site/DCM data, global metadata/counts and both installation-order scheduling remain coordinator-owned. Existing DCM Container ID `mealie` merges with an App of that same ID without an alias; its historical image/SECRET_KEY fields are not this App's deployment contract.
- Focused source/fake verification does not establish actual image startup, native/rendered values, lifecycle preservation, backups/restores, both installation orders or zero outbound behavior of the complete upstream image. No Docker/browser/installer/provider action was executed. Optional scraping, imports, mail/OIDC and upstream scheduled behavior remain outside this slice's runtime evidence.
