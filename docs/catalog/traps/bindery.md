# Bindery traps

## Product and deployment

- Bindery is [vavallee/bindery](https://github.com/vavallee/bindery), a Go/SQLite ebook and audiobook manager, not a Readarr alias. Keep the separate Readarr DCM Container and its Templates unchanged.
- The official [deployment guide](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/docs/DEPLOYMENT.md) publishes `ghcr.io/vavallee/bindery:latest` as the tagged release track, with linux/amd64 and linux/arm64 support. No database, downloader, indexer or metadata-account companion is required to start the App.
- The [image](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/Dockerfile) is distroless and has no shell, curl, s6 or gosu. Use the Compose `user:` field to select the media UID/GID. `BINDERY_PUID` and `BINDERY_PGID` are only optional identity assertions, not user switchers. Keep the native `/bindery healthcheck`; `/ping` is not this App's readiness endpoint.
- The UI, API and OPDS server listen on container port 8787, independently of the allocated host port. Preserve the selected bind address and the internal service name `bindery`.
- SQLite, artwork, cache and App backups persist under the private App-local `/config` mount. A kept `config/.keep` prepares the directory without writing Bindery configuration or reading credentials. Ensure that directory is writable by the selected `user:` before starting; do not recursively change ownership of existing data.

## Storage and preservation

- Fresh shared Projects expose one `${DATA_ROOT}:/data` parent, with library default `/data/media/books` and download default `/data/torrents`. Existing legacy layouts retain `${MEDIA_ROOT}:/media` and `${DOWNLOADS_ROOT}:/downloads`, with defaults `/media/books` and `/downloads`. Configuration stays separate from media. An absent layout keeps the legacy paths.
- Existing root folders, quality and metadata profiles, provider identity, audiobook defaults, naming, import mode and download-client path remaps are person-owned. Setup reads root IDs and paths; it does not register, normalize, move, scan or import anything. Create missing books subfolders with the intended ownership when selecting them. Do not change a paired ebook/audiobook library into separate roots implicitly.
- `BINDERY_DOWNLOAD_DIR` is not a watch folder: import paths normally come from each download client's API. Automatic download/indexer Links are not implemented. Bindery's flat provider JSON is not Servarr's `implementation`/`fields` schema; copying a Readarr or qBittorrent Link would target the wrong contract.
- A shared mount is not proof that imports hardlink on the selected storage. Media files are not included in ordinary Project Backups; plan their backup separately. Non-purge removal must keep configuration and media.
- Separate media App identities remain outside this initial slice. Bindery is not in the LinuxServer-only identity list, and its importer directory-mode setting does not support 0775. Do not invent a UMASK environment contract or expand shared identity handling from this App package.
- `BINDERY_DOWNLOAD_RETENTION_DAYS="0"` keeps finished download records by default instead of accepting the upstream 90-day cleanup policy. This does not change library/profile rows or explicitly saved person-owned settings.

## Setup and credentials

- **Partial implementation:** Setup verifies an existing administrator, API key and explicit root-folder list. First-account creation, API-key bootstrap/issuance and the native Homarr Link are not implemented in this App-only slice. A healthy container or empty root list alone does not satisfy Setup.
- If first-run Setup is still required, finish administrator creation in Bindery using the Admin login from `self-host credentials`, then retry `self-host setup bindery`. An existing account is never replaced or reset. Missing/ambiguous bootstrap, wrong login and rate limiting remain actionable Manual steps, not automatic retries or a new provenance record.
- Verification requires local administrator login with authentication mode `enabled`. Existing Disabled, Local-only, Proxy or SSO-only configuration is a Manual review boundary; Setup does not weaken authentication or overwrite that choice. It confirms the session's exact username and administrator role separately from the instance key.
- Bindery has one full-access instance API key, not a scoped read-only Homarr key. Recover the existing key privately from Settings → General → Security. The recovery-only `api_key` input stores it as `BINDERY_API_KEY` through the Project credential boundary. `--set-file bindery.api_key=PATH` accepts an owner-only file during an explicitly approved install/reinstall; review and preserve manual Compose edits before approving replacement. Never put the value in arguments, output or chat.
- This slice deliberately does **not** pass `BINDERY_API_KEY` into the container as an upstream first-start seed or generate a replacement secret. That upstream environment variable only seeds a missing database key; changing it does not recover an existing one. Lost/rejected keys remain Manual. No regeneration endpoint, `/auth/config` key discovery, database scraping, account creation or password change is invoked.
- Read-only verification proves an unauthenticated protected status request is rejected, the saved key returns release version/commit, and the key can read a well-formed root-folder array. An explicit empty array is valid after positive administrator/key checks. Missing/null/error-shaped responses, duplicate IDs and relative paths are not an empty library. All body/authentication failures use fixed diagnostics rather than echoing server responses.
- Authentication and API sources: [API guide](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/docs/API.md), [auth handlers](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/internal/api/auth.go), [bootstrap and status](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/cmd/bindery/main.go), [root folders](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/internal/api/root_folders.go).

## Startup actions and deferred Homarr acceptance

- The supported `BINDERY_TELEMETRY_DISABLED="true"` disables telemetry before its startup ping, without changing a database setting. This matters even for an empty fixture. See the [telemetry client](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/internal/telemetry/client.go#L337-L347) and [setting descriptor](https://github.com/vavallee/bindery/blob/ca24961c4c04f58a1cd96c2b8382b87f7eda215f/internal/api/settings_registry.go#L217-L220).
- Existing populated configuration can still run its own scheduled provider actions, imports or searches at startup. Source implementation and fake HTTP tests do not authorize running it. Any later acceptance must use the centrally approved fresh synthetic fixture, contain provider actions and record image/API identities afresh; do not reuse real books, accounts or Projects.
- The eventual exact Homarr kind is `bindery`, secret alternative `apiKey`, initial native widget `mediaMissing`. Bindery has no supported Stats or calendar binding in the inspected Homarr contract. `releases` tracks software versions, not book releases; no release repository/feed is registered by this slice.
- Homarr's inspected adapter discards Bindery queue `partial`/`staleClients` diagnostics and may drop relative artwork URLs. Meaningful missing/queue validation, shared envelope/count helpers, ownership lifecycle, both installation orders and rendered/native acceptance remain pending. Do not substitute a navigation tile, registration or cached empty data for those gates. Wait for the reviewed shared helpers and credential-issuance contract rather than adding temporary copies.
