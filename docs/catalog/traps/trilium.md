# Trilium traps

## Deployment and storage

- This App uses the maintained [TriliumNext/Trilium](https://github.com/TriliumNext/Trilium) project, not the historical zadam image. The official image is `triliumnext/trilium:v0.106.1`, with HTTP on container port 8080 and App-relative `./data` mounted at `/home/node/trilium-data`. It needs no separate database or queue container. The [official Docker guide](https://docs.triliumnotes.org/user-guide/setup/server/installation/docker.html) explicitly warns against `latest`: updates can change the client/server sync protocol. The versioned tag is an intentional exception to the Catalog's usual floating-image convention. Preserve custom image references and review all sync clients before an explicitly approved update.
- The image's [Dockerfile](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/apps/server/Dockerfile) supplies its health check and data-directory environment. Its [startup script](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/apps/server/start-docker.sh) starts as root, recursively assigns `/home/node` to its node user, then runs the application as that user. Keep the mount narrow and App-owned; never point it at an existing unrelated directory. Do not add `privileged`, a Docker socket, LinuxServer PUID/PGID variables, a rootful `user:` override or a second recursive ownership migration. The official rootful image supports `USER_UID`/`USER_GID` for explicitly reviewed custom configuration; this App keeps its upstream defaults.
- The entire [data directory](https://docs.triliumnotes.org/user-guide/setup/data-directory.html) matters: `document.db`, SQLite companions, `config.ini`, backups and other App data. Ordinary restart/update/non-purge removal must retain that directory. Keep separate [Backups](https://docs.triliumnotes.org/user-guide/setup/backup.html). External custom database/backup paths are not automatically covered by archiving this App's folder, and a Restore can interact with all members of a sync group.
- The Compose definition does not initialize a database, seed demo notes, configure sync, register an account or grant public Access. This slice has no Docker, startup/network, browser, Backup/Restore or live lifecycle acceptance. Review any existing sync configuration and source-controlled/user scripts before a centrally approved runtime attempt.

## Setup and authentication

- Trilium has one notebook password, not a username/administrator-user API. The App's Setup only verifies an existing password against the fixed installed endpoint; it does not create or adopt account ownership. Fresh notebook, sync, Restore, unset-password, partial-sync and recovery states stay an actionable Manual step. The owner must choose the intended notebook and complete first initialization themselves. Automatic bootstrap is not implemented in this slice.
- The read-only admission checks [setup/status](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/packages/trilium-core/src/routes/api/setup.ts), requires the protected application-info route to reject an anonymous request, reads the [bootstrap login state](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/apps/server/src/routes/index.ts), and signs in using the existing [password form](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/apps/server/src/routes/login.ts). It does not follow login redirects, attempt SSO/TOTP, consume recovery codes or change authentication settings. Success requires explicit authenticated initialized/password-set flags and meaningful protected [application/build/sync information](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/packages/trilium-core/src/services/app_info.ts), including the same sync protocol reported by setup/status. HTTP 200 or container health alone never completes Setup.
- `POST /etapi/auth/login` is **not** a password probe: every successful call creates a permanent token. Setup and Check never call it or any token, note, SQL, password-reset, sync, start-over or Restore mutation endpoint. Session cookies stay in the invocation's existing helper session; response bodies, cookies and note content are never logged as diagnostics.
- Preserve a rejected or missing Project password and reconcile it privately with its known notebook. Do not reset Trilium to make it match the shared Admin login. Upstream warns that [password reset permanently loses protected notes](https://docs.triliumnotes.org/user-guide/setup/server/auth/password-reset.html); upstream examples that disable authentication or edit SQLite are not operations this App performs. Keep existing sync and account recovery settings intact, then retry `self-host setup trilium` after the legitimate prerequisite is resolved.

## Native Homarr remains held

- Homarr's exact integration kind is `trilium` and its supported surface is [Stats](https://homarr.dev/docs/integrations/trilium/): `version` (`text`), `notesCount` (`count`), and `dbSize` (`bytes`) from TriliumNext >=0.94.0. There is no Trilium note-content widget to substitute. The connector and metric/count validation are deferred to the accepted shared Homarr helpers; this App-only slice installs no native integration or widget.
- [ETAPI token authentication](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/apps/server/src/etapi/etapi_utils.ts) and the [token service](https://github.com/TriliumNext/Trilium/blob/2be0c6ed7867fca60c3ed315b449952b536efe75/apps/server/src/services/etapi_tokens.ts) provide **unscoped notebook API access**, not read-only or metrics-only permissions. Do not advertise a fictional scope, generate a substitute token locally, scrape SQLite, blindly rotate credentials or revoke a token used by somebody else's integration. Issuance waits for the reviewed shared non-idempotent credential helper.
- The application-info response has no persistent notebook UUID. Versions, build metadata, process timestamps, equal/zero counts and possession of a potentially synchronized token do not establish the selected notebook's persistent identity. Do not infer a notebook from private note content. Native wiring remains Manual while that identity cannot be positively established.
- When Homarr is installed, both Setup and Check explicitly retain the Manual `homarr-key` prerequisite even if a saved ETAPI token/ID/pending record exists; those records are preserved without being adopted, issued, replaced or finalized. Reconcile the intended notebook and known credentials privately and wait for supported ownership/identity verification before retrying. No native, rendered, both-install-order or removal/reconnect acceptance is claimed.
