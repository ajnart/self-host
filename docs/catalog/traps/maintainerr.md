# Maintainerr traps

## Deployment and private persistence

- The official `ghcr.io/maintainerr/maintainerr:latest` image supports amd64/arm64, serves the UI/API on TCP 6246, and persists SQLite and App-managed files under `/opt/data`. No separate database or Redis is required. The image supports Compose `user: UID:GID`; this App uses the Host PUID/PGID, not unsupported identity environment variables. The image's healthcheck verifies database readiness, not completed Setup. [Installation](https://docs.maintainerr.info/installation/), [inspected Dockerfile](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/Dockerfile), [SQLite configuration](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/app/config/typeOrmConfig.ts).
- `data` is a persistent App-local bind mounted at `/opt/data`. Maintainerr stores connected-service credentials unencrypted in its database: protect this directory and every Backup as credentials. The read-only preflight requires real App/parent/data directories and mode 0700 on `data`; it never creates directories, reads the database, changes permissions or infers ownership from emptiness. The long bind syntax uses `create_host_path: false` to refuse automatic host-directory creation. [Security](https://docs.maintainerr.info/security/), [Compose bind syntax](https://docs.docker.com/reference/compose-file/services/#long-syntax-6).
- Automatic private-directory creation is pending a narrow Project/storage-owner helper. Until then, installation needs an explicitly prepared `apps/maintainerr/data` directory writable by the selected container identity. Missing, symlinked or non-private directories remain Manual. Existing data, ownership and permissions are never silently migrated. The mode check does not prove rootless UID mappings, ACL policy or actual container writability; those still require reviewed storage preparation and runtime acceptance.
- The official entrypoint and image healthcheck are retained. No media/download mount, host networking, device, privileged mode, Docker socket or automatic media-server installation is added. The optional upstream media mount enables leftover-folder cleanup and is deliberately omitted. [Startup script](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/docker/start.sh).
- Maintainerr's optional weekly telemetry is disabled using its supported `TELEMETRY=off` environment setting. This is separate from self-host's Telemetry. No runtime acceptance or containment of every upstream startup metadata/version request is claimed. Existing App rules may run according to their existing schedules when the App runs; Setup neither runs them nor changes their schedules. [Telemetry/security](https://docs.maintainerr.info/security/).

## Authentication and owner prerequisites

- Maintainerr has no built-in login or inbound API authentication. Its Settings API key does not protect requests; Setup neither issues nor copies it. Anyone who can reach the App can read credentials and change rules. Preserve private Access and any existing authenticating proxy; do not publish the port publicly or remove authentication to make verification pass. [Security](https://docs.maintainerr.info/security/), [API conventions](https://docs.maintainerr.info/api/).
- The person must select and configure exactly one Plex, Jellyfin or Emby server in Maintainerr's Services UI. Plex needs administrator authentication and explicit server selection. Jellyfin/Emby need suitable credentials and administrator selection. Setup does not enroll an external account, choose a replacement backend, change Plex TLS settings, copy keys from settings/database endpoints or configure optional Arr/download integrations. [Configuration](https://docs.maintainerr.info/configuration/).
- An unconfigured server is a Manual prerequisite, not a meaningful zero-media success. Repair the selected server privately and test its connection, preserving credentials, libraries, rules, collections and retention, then run `self-host setup maintainerr`. Lost/rejected credentials are repaired through Maintainerr's existing supported UI boundary, not rotated by self-host.

## What Setup verifies

- Checks database-ready response fields, the explicit configured boolean, supported backend type and nonempty server machine identity/version. The configured flag checks settings presence only; public media-server identity alone is not authentication. [Health controller](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/app/health.controller.ts), [setup flag](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/modules/settings/settings-data.service.ts), [media-server controller](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/modules/api/media-server/media-server.controller.ts).
- For Plex, requires its existing connection-test response to confirm authenticated library access as well as identity. For Jellyfin/Emby, requires a positive user-ID list from their authenticated adapters. An explicit empty library list is valid after those checks. Reads the selected type/identity again to reject a server switch during verification. [Plex connection test](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/modules/api/plex-api/plex-api.service.ts), [test response](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/modules/settings/settings-operations.service.ts), [Jellyfin adapter](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/modules/api/media-server/jellyfin/jellyfin-adapter.service.ts), [Emby adapter](https://github.com/maintainerr/maintainerr/blob/aa0ed0d9e8e080799943e1344214159f84625355/apps/server/src/modules/api/media-server/emby/emby-adapter.service.ts).
- Upstream Jellyfin/Emby cache user/library responses and swallow some provider failures. These observations are not an uncached token-revocation guarantee or proof of a real runtime connection. The tests exercise source-backed synthetic contracts only. Raw responses, provider errors, machine/user/library names and credentials are not included in Setup output.
- All requests are read-only GETs, with redirects refused. No settings replacement, credential generation/deletion, server switch, rules/collections/retention change, job execution, cleanup, library-size enumeration or media deletion is performed. Reruns re-verify existing configuration without adding authority flags, journals or identity records.

## Deferred native coverage

- This is an App-only source slice, not complete #164 acceptance. Catalog/site/DCM registration and metadata/count updates remain coordinator-owned. No Homarr leaf is added yet.
- The researched Homarr kind is `maintainerr`, with an advertised empty credential alternative and only shared Stats support. The planned metrics are `itemsHandled`, `episodesHandled`, `moviesHandled` (count) and `reclaimable` (bytes). No Stats/count/media-envelope implementation is copied into this App slice. [Homarr provider](https://github.com/homarr-labs/homarr/blob/df8d03b13452bb50c55a424187e1fa188ab510d2/packages/integrations/src/stats/providers/maintainerr.ts).
- Later connector work must use reviewed shared dependencies and prove a genuinely advancing authenticated Homarr Stats refresh. Explicit zero history/reclaimable values can be valid only with positive configured-server verification; do not run cleanup or alter a rule to manufacture history. Native, rendered, both-order scheduling, preservation and lifecycle/runtime evidence remain unperformed.
- Research-time release tags and resolved `latest` OCI revisions differed: Maintainerr release `v3.31.0` versus image source revision `aa0ed0d9e8e080799943e1344214159f84625355`, Homarr release `v2.10.1` versus image source revision `df8d03b13452bb50c55a424187e1fa188ab510d2`. Relevant inspected contracts matched, but actual runtime API versions must be recorded separately. Floating tags and release metadata are not runtime acceptance or a fixed compatibility allowlist.
