# RomM traps

## Deployment and persistence

- The official `rommapp/romm:latest` image was inspected as 5.4.1 at source `9c74d0143fbb876f2f62260b91c6fd0b3f590226`. Runtime image identity and API version still require a separately approved check; a release tag is not that evidence.
- `romm-db` is a dedicated `mariadb:11` dependency, health-gated with its official `healthcheck.sh`. Only RomM's 8080 web port is published through the selected bind address; database and embedded Valkey ports stay unpublished. Preserve the selected backend, Compose service names and existing mounts.
- `./data:/romm` retains configuration, resources and personal assets. `./redis:/redis-data` persists the image's embedded Valkey; no extra Redis container is needed. `./database` retains MariaDB. Non-purge removal retains these paths and the library.
- The library is `${MEDIA_ROOT}/romm`, mounted at `/romm/library`, outside App configuration backups. Prepare that approved directory before installation; read-only Preflight never creates it or changes existing permissions, and Compose uses `create_host_path: false`. It is not an authority for first-admin creation. Do not relocate an existing library, adopt another installation's paths or change Unix ownership automatically. Back up the library separately.
- The official image does not implement LinuxServer PUID/PGID environment remapping. Preserve its image-specific identity behavior; arbitrary UID/GID overrides and rootless namespace mappings are not validated here. No separate-media-user or hardlink support is claimed.
- The signing key is 64 hexadecimal characters, generated once with separate application-database and root-database passwords. Keep those private Project values; rotating the signing key invalidates sessions and outstanding invites. Never replace credentials to make Setup pass.

## Setup and recovery

- Setup reuses `firstadmin.FirstAdmin` and the existing HTTP/session helpers. An anonymous `/api/users/me` must reject access with 401, and HTTP Basic authentication must return a positive account ID, the expected username, explicit enabled state and exact `admin` role. HTTP 200, public statistics and kiosk access do not establish an administrator. Existing accepted accounts are verified without account writes.
- Automatic creation requires an independently read, valid RomM 5.4.1-or-newer 5.x heartbeat with explicit `SYSTEM.SHOW_SETUP_WIZARD: true`. Upstream sets that flag only when no administrator exists and its setup wizard is enabled. Missing, null, malformed, old/new-major, protected or redirected responses never prove absence. An earlier authentication error also prevents creation.
- Creation remains anonymous and carries the server's `romm_csrftoken` cookie and matching CSRF header to `/api/users`. The upstream route refuses anonymous creation after an administrator exists, including a competing first-admin race. Setup validates the 201 response and checks that authenticated readback has the same returned account ID. No fresh-directory flag, local provenance journal, token issuance or database edit is used.
- Rejected existing credentials, missing CSRF, changed post-creation identity and uncertain creation responses remain actionable Manual steps. Preserve users/profiles and the database, sign in through RomM using the existing Admin login or finish its first-admin page, then retry `self-host setup romm`. A retry verifies working credentials first; it does not rotate or reset them. Existing-account checks positively verify the current returned identity but do not introduce a cross-run ownership/provenance journal.
- RomM lowercases new usernames. Setup records an App-local `ROMM_ADMIN_USER` alias when normalization is necessary, without changing the shared Admin login. Supported new usernames are 3–255 ASCII letters, digits, underscores or hyphens; passwords must be 6–255 ASCII characters. Existing accepted credentials are not rewritten to satisfy new-account validation.

## Authentication, data and runtime boundaries

- Keep authentication, download authorization and CSRF protection enabled. Fresh Compose explicitly disables kiosk and download-auth bypass. Setup never edits these flags, user profiles, metadata-provider credentials or library configuration on rerun.
- No ROM/firmware download, scan, import, metadata-provider probe, asset request or sync action is part of Setup/Check. Watchers, scheduled scans/metadata refreshes, sync and configured telemetry are disabled in the generated starter. The inspected upstream startup can rebuild an outdated Switch TitleDB cache independently of the scheduled-task flag; until separately contained/approved, this definition is **runtime-held**, including existing caches. No runtime was executed for this slice.
- Upstream `/api/stats` is public and returns global aggregates even with normal authentication enabled. That does not make library content or per-user data public by intent. Homarr advertises exact kind `romm` with only empty secrets and Stats support; protected metrics must remain Manual rather than weakening authentication, bypassing TLS or inventing credential alternatives.
- Upstream nginx serves metadata resources under `/assets/romm/resources/` directly, while `/library/` and `/cache/` are internal locations. Do not claim all metadata assets are protected by the API login. Do not connect populated private resources, broaden Access or fetch assets for acceptance. New isolated empty storage is the only planned runtime scenario, and still needs explicit approval.
- This first slice has no Homarr descriptor, Stats/count parsing, widgets or managed native binding. Those wait for #147's accepted shared contract. Catalog registration, generated site/DCM exports, icon/stars metadata, counts and global documentation are coordinator-owned follow-ups. Native/rendered/lifecycle acceptance and both installation orders remain unperformed.
