# Healthchecks traps

## Deployment and persistence

- The official `healthchecks/healthchecks:latest` image was researched at v5.0.3, source `51a503531d845fc11d5ef270d576c59c300e3620`. It serves HTTP on container port 8000 and runs as its own `hc` user. It does not implement LinuxServer's PUID/PGID or `/config` contract.
- The App includes its own PostgreSQL 16 service, waits for database health and stores its data under `apps/healthchecks/database`. PostgreSQL contains users, projects, checks, ping history and notification channels. Keep that directory and the Project's private credentials together through Backup/Restore; normal removal must not purge them.
- App-scoped `DB_PASSWORD` and `SECRET_KEY` use the existing private Project environment boundary. They are not the entire Project environment. This avoids mounting host-owned mode-0600 files that the official image's unrelated `hc` identity cannot read. Never rotate either secret as a Setup retry. Current API keys are HMAC-hashed using `SECRET_KEY`; replacing it invalidates their hashes.
- The official entrypoint already runs migrations, alert processing and looping reports. Do not add duplicate workers or replace its command. No SMTP listener is enabled by default. Outbound email needs separately reviewed SMTP configuration; a working web page does not prove notification delivery.
- New definitions close registration and retain upstream blocking of private-address notification integrations. Existing Compose edits remain authoritative; do not enable private-IP requests, registration, external authentication or public Access to make verification pass.

## Setup and credential boundary

- Automatic administrator bootstrap and project creation remain Manual without proved first-administrator authority. Setup never creates bootstrap-authority markers or infers an empty database. The native Homarr leaf and project read-only key issuance are implemented, with central Catalog/target assembly and native/rendered/lifecycle runtime acceptance still pending.
- Healthchecks signs in by email. A plain shared Admin username maps to `<username>@selfhost.local`; an existing email-shaped username is kept. Setup verifies the actual authenticated profile and exact selected project owned by that account. Other accounts, memberships, MFA and project identities are never changed to gain access.
- On an independently confirmed fresh instance, use the official image's interactive `createsuperuser` management command in its container. Do not put passwords in argv. Unlike Django's stock command, Healthchecks does not support assuming `--noinput` or `DJANGO_SUPERUSER_PASSWORD`. A duplicate email is rejected, not reset. On an existing instance, recover the known account explicitly; Setup does not query its database or invent evidence of freshness.
- Supply the exact project's UUID from its checks-page Address as `healthchecks.project_id`. Setup does not choose the first project, create a new project, transfer ownership or adopt a membership. A missing, mismatched or non-owned selection remains Manual.
- Supply only that project's known read-only key through `healthchecks.homarr_api_key` private-file recovery input; `healthchecks.homarr_key_ownership` restores its matching private record when available. An explicitly supplied existing key is reused and its owner/project/badge/fingerprint recorded only after positive read-only identity and check validation. These are never generated deployment secrets or container environment variables. Private-input ingestion currently requires install, which can replace Compose: review and separately approve replacement before using it. There is no claimed credentials-only ingestion command. Empty input preserves saved values.
- A lost/rejected key, mismatched ownership or unknown populated read-only slot remains Manual. Restore the matching Backup/secret and ownership or explicitly reconcile only the recorded project's read-only credential. Never revoke write or ping keys, clear pending evidence to retry issuance, choose another project to escape a hold or blindly POST `create_key`: upstream replaces that slot and returns its new secret only once.
- When both saved key and ownership are absent and the selected owned project's read-only slot is positively empty, Setup uses the reviewed `helpers.CredentialIssuance` operations `Pending`, `Begin`, `Capture`, `Commit`. It records the exact owner/project/badge intent before the one provider POST and rereads slot absence immediately before that POST. The provider offers no atomic create-if-empty operation: concurrent edits between that final read and POST remain a runtime/coordination limitation, not a claimed lock.
- Only the selected one-time `key-created-modal` supplies issued evidence. A complete unique readonly input is captured **before** HTTP status, key format, identity, scope or check semantics can reject the outcome, even when following modal markup is truncated. Incomplete outcomes remain Manual without commit or reissue. Every candidate is registered only for in-memory redaction; ambiguous outcomes persist only nonsecret metadata and no candidate secrets. A malformed journal, foreign intent, uncertain uncaptured outcome or conflicting active record cannot issue another key. A valid captured key can complete interrupted private persistence after fresh verification without a second provider POST; malformed/error-status outcomes remain Manual.

## Read-only verification and preservation

- `/health` only proves database readiness. Setup separately authenticates the saved Admin login using the existing cookie/CSRF helper, verifies profile identity and owned-project selection, and matches the selected project's stable overall badge identity to the read-only badges API **before** reading Management API v3 check data. Homarr verifies that same identity and expected read-only channels denial through its recorded integration before acquiring Stats; manually replacing its credential with a same-project write key cannot pass on matching badge/counts alone.
- Read-only keys may be legacy plaintext or current `hcr_` keys. The App does not infer scope from a prefix: accepted check/badge reads are combined with an expected 401 from the **read-only GET** of the write-key-only channels inventory. A successful channels read is rejected. No permission test writes a check, sends a ping or changes a notification.
- Check responses must contain an explicit list, stable read-only check identifiers, nonnegative ping counts and known `new`, `up`, `grace`, `down` or `paused` statuses. Write-capable fields, missing/null lists, body errors, unknown statuses, duplicate identities and unauthenticated pages are rejected without logging raw data. A truly empty list is valid only with the independent authenticated selected-project identity checks.
- The official administrator command creates `My First Check` and an email channel. Preserve them. The untouched check is `new`, not `up`; Setup must never ping it or mark a job successful. Existing schedules, identifiers, ping addresses, notification jobs and channels remain unchanged. Real jobs and delivery tests require a separate person decision.
- `site_root` sets the initial browser origin; `ping_endpoint` optionally sets displayed ping addresses and must end with a slash. Neither provisions a proxy or rewrites incoming routes. Existing ping bases are not automatically migrated when Access changes. Review related proxy/Host settings explicitly; do not weaken TLS or overwrite user Compose to repair them.
- Homarr's exact `healthchecks` kind uses the App-owned project read-only key as `apiKey`, internally at `http://healthchecks:8000`, and supports only shared Stats `checksUp`, `checksDown`, `checksGrace`, `checksNew`, all in counts. The leaf consumes one central catalog/snapshot/forced refresh per verification invocation and the reviewed count validator, including explicit zero values and required successful retry metadata. Paused checks are omitted from the counters, so their sum is not a total. No native/rendered/lifecycle acceptance is claimed from source/fake contracts or registration; central assembly is still required.
